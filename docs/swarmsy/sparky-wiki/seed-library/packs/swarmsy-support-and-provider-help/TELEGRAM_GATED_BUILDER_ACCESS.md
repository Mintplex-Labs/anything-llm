# Telegram-Gated Builder Access Foundation

This document defines the current foundation for future Open Runtime, app editing, remix, export, and community build access.

## Scope

This is a gating/settings foundation only.

- Open Runtime is not implemented.
- App editing/remix/export/community build features remain locked.
- Rewards, XP, leaderboard, factions, seasons, and Telegram reward sync remain website/Telegram-owned.
- The app does not create a new account system or backend authority.
- Official master/core remains protected.

## App Behavior

Settings now includes **Community Builder Access / Runtime Builder Access**.

Default state is locked:

```txt
Connect Telegram via GKnifty Heads Incubator to unlock community builder/runtime editing.
```

The **Connect Telegram** button opens:

```txt
https://cryptomoonboys.com/gkniftyheads-incubator.html
```

The **I've connected - refresh access** button refreshes the local access placeholder. Until an app-readable verified handoff exists, refresh moves the state to:

```txt
Pending verification
```

Future builder entry points must call `isRuntimeBuilderAccessUnlocked(...)` and remain locked unless a future server-issued proof/token exists and passes validation. This foundation does not currently unlock from a public source string or plain local state.

## Website/Auth Flow Investigation

Files inspected in `Crypto-Moonboys/Crypto-Moonboys.github.io`:

- `gkniftyheads-incubator.html`
- `js/identity-gate.js`
- `js/incubator-link.js`
- `js/core/moonboys-state.js`

Current flow:

1. User opens Telegram and starts `@WIKICOMSBOT`.
2. User runs `/gkstart`.
3. User runs `/gklink`.
4. Bot sends a signed one-time link back to `gkniftyheads-incubator.html#telegram_auth=...`.
5. `incubator-link.js` parses `telegram_auth` from the hash.
6. The page posts the payload to `/telegram/link/confirm`.
7. On success, `identity-gate.js` stores Telegram identity and marks `telegram_linked`.
8. `restoreLinkedTelegramAuth` can recover linked auth through `/telegram/user/status` when a valid API base is available.

The cleanest future app handoff is an app-readable verification code or signed token generated by the same web/auth flow after `/telegram/link/confirm`. The app should exchange or validate that code against Crypto Moonboys auth, then persist only a non-secret linked-access marker. A local checkbox/toggle must never be enough for final unlock.

## Security Boundary

- Do not trust plain local toggles for final unlock.
- Do not export OpenAI keys, local secrets, provider settings, or reward/sync state as part of builder access.
- Do not let builder access alter rewards/backend systems.
- Telegram identity truth comes from the Crypto Moonboys web/auth flow.
- The app stores only a local access placeholder for future builder-entry gating.

## Current Implementation

- `src/storage/communityBuilderAccessStorage.ts` stores fail-closed local access state.
- `refreshCommunityBuilderAccess()` returns `pending-verification` unless future proof validation unlocks access.
- `saveVerifiedCommunityBuilderAccess()` remains fail-closed until a future server-issued proof/token validator exists.
- `isRuntimeBuilderAccessUnlocked()` returns true only when future proof validation passes; today it always fails closed.
- `doesCommunityBuilderAccessUnlockRewardsOrBackend()` always returns `false`.

## Required Future Work

- Add a website-generated deep link, signed token, local copy code, QR/link code, or app-readable verification code.
- Add app-side verification against Crypto Moonboys auth.
- Keep builder unlock separate from rewards, XP, factions, leaderboard, backend reward authority, and Open Runtime implementation.
