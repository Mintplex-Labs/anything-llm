# Networked Website Future

Status: PR154 doctrine foundation. This document describes the future web direction for SPARKY Wiki. It does not add APIs, provider calls, Open Runtime, source editing, backend, rewards, Telegram sync, website changes, or new UI surfaces.

## Websites Are Becoming Agent-Readable Systems

SPARKY Wiki's thesis is that future websites may increasingly become more than page trees. They may act as interactive knowledge systems that expose structured state, routes, source maps, protocols, claim maps, data contracts, and reasoning boundaries to humans and agents.

Future sites should be able to answer:

- what do you know?
- where did that claim come from?
- which claims are verified, disputed, inferred, or lore?
- what protocols explain this mechanic?
- what APIs or local actions exist?
- what is safe, planned, live, or blocked?
- what changed since the last version?

SPARKY Wiki is shaped for this future. The browser-first app, local wiki/reference layer, Offline Wiki Ledger, Knowledge Graph, Cultural Protocol Engine, Identity Forge, Runtime Action Kernel, and Widget/Workspace foundations are separate layers so humans and future agents can inspect the same structure.

## Agent-Readable Websites

Agent-readable does not mean handing agents full authority. It means a site can expose clear, structured knowledge:

- current truth docs
- API-aware docs
- local action ids and risk labels
- provenance and source-card schemas
- claim maps and citation indexes
- protocol definitions
- knowledge graph summaries
- workspace/user context boundaries
- provider and network boundaries
- freshness warnings

Sparky should use these records before weak generic provider replies. Future external agents should be able to read the same boundaries without guessing.

## Cross-Site Communication

SPARKY Wiki's future web model expects cultural archives, project websites, identity systems, and creator workspaces to increasingly communicate through structured references instead of only screen scraping.

Examples of future-safe structures:

- source cards
- claim IDs
- branch IDs
- protocol IDs
- action IDs
- pack readiness
- cited public evidence
- founder thesis labels
- freshness warnings

This PR does not build cross-site communication. It documents why the local archive is structured that way.

## Local-First Matters

Local-first/offline intelligence keeps the user from depending on a provider for basic app truth, wiki recall, protocol explanation, source labels, and current build boundaries.

Offline does not mean anti-network. It means the app has a durable local base:

- Sparky core truth first
- workspace/user documents second
- compressed Knowledge Graph records third
- full wiki/protocol docs fourth
- live provider/web lookup only when connected and needed

## What SPARKY Wiki Must Not Claim Yet

- no live public API layer is built in this PR
- no Open Runtime is built
- no source editor is built
- no autonomous web agent is built
- no provider-created actions are trusted
- no website repo changes are included
- no rewards/backend/Telegram sync authority changes are included
